## 1. Что происходит, когда вводишь URL в браузере

**Короткая версия:** DNS → TCP → TLS → HTTP → рендеринг.

- **DNS.** Кэш браузера → кэш ОС → `/etc/hosts` → резолвер (порядок на Linux — `/etc/nsswitch.conf`). Если ответа нет, резолвер делает **рекурсивный запрос**: корневые серверы → зона `.com` → **авторитативный** сервер домена. Ответ кэшируется на **TTL**.
- **TCP.** Рукопожатие SYN → SYN-ACK → ACK на порт 443. По пути — маршрутизация, ARP, NAT (шлюз делает DNAT на сервер в DMZ).
- **TLS.** Клиент передаёт **SNI** (имя сайта). Сервер присылает **сертификат**, браузер проверяет цепочку доверия, домен и срок действия. Согласуется сеансовый ключ, дальше шифрование **симметричное**.
- **HTTP.** `GET /` с заголовком `Host`. Reverse proxy (Nginx) передаёт запрос бэкенду, тот возвращает ответ с кодом статуса.
- **Рендеринг.** Разбор HTML, догрузка CSS/JS/картинок (keep-alive, HTTP/2), отрисовка.

**Посмотреть своими глазами:**
```bash
dig +trace example.com
curl -v https://example.com
openssl s_client -connect example.com:443 -servername example.com
```

**Дополнительные вопросы:** рекурсивный vs итеративный DNS-запрос; почему после смены IP сайт открывается не у всех сразу; зачем SNI; почему симметричное шифрование после рукопожатия; HTTP/2 vs HTTP/1.1, что такое HTTP/3 (QUIC); 502 vs 504.

## 2. Контейнер vs виртуальная машина

**Ключевое отличие — общее ядро.** Контейнеры используют ядро хоста, у ВМ своё ядро и своя ОС поверх виртуального железа (гипервизор).

Следствия:
- **скорость и вес:** контейнер стартует за доли секунды и весит мегабайты, ВМ — гигабайты и загрузка ОС;
- **изоляция:** у ВМ сильнее (граница — гипервизор); уязвимость ядра может позволить выйти из контейнера на хост, поэтому не запускаем контейнеры от root;
- **совместимость:** на Linux-хосте не запустить контейнер с ядром Windows (Docker Desktop на Windows/Mac запускает Linux в скрытой ВМ).

**Три кирпичика контейнера:**
- **namespaces** — что процесс **видит**: pid, net, mnt, uts, ipc, user;
- **cgroups** — сколько ресурсов может **потреблять**: CPU, память, I/O (`docker run --memory=512m --cpus=1`);
- **OverlayFS** — файловая система из слоёв образа (только чтение) + тонкий слой для записи. Поэтому контейнеры из одного образа экономят место, а данные пропадают после `docker rm` без тома.

**Формулировка:** «Контейнер — обычный процесс на хосте, изолированный namespaces, ограниченный cgroups, с файловой системой из слоёв образа. Отличие от ВМ — общее ядро: лёгкость и скорость, но изоляция слабее».

**На практике (блок Docker):** найти процесс контейнера в `ps` на хосте, посмотреть `/proc/<PID>/ns` и cgroups.

## 3. Merge vs rebase

**Мой ответ:** не знаю.

Обе команды переносят изменения из одной ветки в другую, отличаются **историей**.

```
Исходно:            C---D   feature
                   /
              A---B---E---F   main

merge:              C---D---M   feature    (новый merge-коммит M,
                   /       /                старые коммиты не меняются)
              A---B---E---F   main

rebase:       A---B---E---F---C'---D'   feature   (коммиты пересозданы,
                                                    новые хэши)
```

- **merge** — безопасно, сохраняет реальный ход работы, но история становится «паутиной»;
- **rebase** — чистая линейная история, но **переписывает** коммиты.

**Аналогия:** merge — оставить свою главу отчёта как есть и пометить «здесь объединил с новой версией». Rebase — заново переписать свою главу поверх свежей версии отчёта, как будто начал после коллег.

**Золотое правило:** не делать rebase опубликованных веток, с которыми работают другие.

**Когда что:**
- rebase — своя локальная ветка перед merge request; `git rebase -i`, чтобы «причесать» коммиты;
- merge — слияние готовой ветки в `main` (через MR), вариант **squash merge**.

### 📝 Задание на потом: лаборатория (5 минут)
```bash
mkdir ~/git-lab && cd ~/git-lab && git init
echo "1" > file.txt && git add . && git commit -m "A"
git checkout -b feature
echo "feature" > f.txt && git add . && git commit -m "C (feature)"
git checkout main          # или master
echo "main" > m.txt && git add . && git commit -m "E (main)"
git log --oneline --graph --all

cp -r ~/git-lab ~/git-lab2
# в ~/git-lab:   git checkout feature && git merge main
# в ~/git-lab2:  git checkout feature && git rebase main
# в обеих:       git log --oneline --graph --all
```
Сравнить графы и хэш коммита C до и после rebase.

## 4. «Зачем тесты в CI, если я запускаю их локально?»

**Мой ответ:** CI проверяет код в чистом окружении (верно, но это один аргумент из пяти).

1. **Не зависит от дисциплины.** CI запускается всегда; можно запретить слияние MR с красным пайплайном.
2. **Тестируется то, что в репозитории.** Локально мешают незакоммиченные файлы, глобальные пакеты, другая версия Python, переменные окружения.
3. **Интеграция с чужими изменениями.** CI может проверить результат слияния с актуальным `main`.
4. **Полный набор проверок.** Интеграционные тесты, несколько версий, линтеры, сканеры — долго для ноутбука.
5. **Ворота для деплоя и история.** Деплой только после зелёного пайплайна; видно, что и когда проверялось.

**Формулировка:** «Локальные тесты — быстрая обратная связь разработчику. CI — обязательная воспроизводимая проверка того, что реально лежит в репозитории, вместе с чужими изменениями, и ворота для деплоя».

## 6. Сценарий: «облако не открывается»

Схема: шлюз (проброс 80/443) → ВМ в DMZ → Nginx → Docker-контейнер приложения на `127.0.0.1:8080` → БД в контейнере.

**Мой ответ:** ping, tracert, nslookup, curl; (а) упал контейнер → `docker compose ps`; (б) Nginx не знает, куда проксировать; (в) перезапустить контейнер, потом искать логи.

**Что хорошо:** подход «от клиента вглубь по уровням».

### Шаг 0. Вопросы до команд
У всех или у части пользователей? Изнутри сети или снаружи? С какого времени? Что менялось? «Утром» — значит, что-то случилось ночью: `uptime` (перезагрузка?), автообновления, `df -h`, `journalctl -k` / `dmesg` (OOM killer?).

### Главное: симптом указывает уровень
| Симптом | Где проблема | Что проверить |
|---------|-------------|---------------|
| **Таймаут** | Запрос не доходит до Nginx: ВМ, шлюз, DNS, провайдер | Статус ВМ в гипервизоре; `ss -tlnp \| grep -E ':80\|:443'`; `curl -I http://localhost` изнутри; правила и логи шлюза; `dig +short` домена = белый IP |
| **502** | Между Nginx и контейнером: на `127.0.0.1:8080` никто не отвечает | `/var/log/nginx/error.log` (`connect() failed (111: Connection refused) while connecting to upstream`) → `curl -I http://127.0.0.1:8080` → `docker compose ps` → `docker compose logs app` |
| **Ошибка БД** | Между приложением и БД | `docker compose ps` → `docker compose logs db` → `docker compose logs app`; `df -h` (БД падает при заполненном диске) |

**Если упал только контейнер — будет 502, а не таймаут:** Nginx жив и отвечает «бэкенд недоступен».

### Поправки
- Ping здесь мало что даёт: ICMP часто закрыт, а пинг домена — это пинг шлюза, не ВМ. Лучше сразу `curl -v` (подробно: TCP, TLS, заголовки) или `curl -I` (только код и заголовки).
- **Сначала логи, потом перезапуск.** Иначе причина потеряется и вернётся.
- Зависимость задаётся в `docker-compose.yml` (`depends_on`), не в Dockerfile. `depends_on` ждёт только **запуска** контейнера, а не готовности БД — нужен `healthcheck` + `condition: service_healthy`.
